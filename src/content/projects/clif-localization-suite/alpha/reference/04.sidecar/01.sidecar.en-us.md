# Key Sidecar

On export, besides the `.clif` files themselves, the plugin also writes a `<manifest stem>.clifmap.json` — the **original key sidecar** — recording the correspondence between "CLIF canonical ID ↔ original UE Namespace / Key".

## Why it is needed

A CLIF name only allows lowercase kebab-case (`[a-z][a-z0-9-]*`), whereas a UE Key is an arbitrary developer string:

```text
UE Namespace = UObjectCategory
UE Key       = MyGame|层|字形微调|阴影染色
```

A Key containing Chinese, `|`, capitals and `/` can never be a CLIF entry ID directly. The CLIF specification itself also states that "engine keys do not live inside CLIF; the converter is responsible for the mapping and may store the mapping out-of-band" — the sidecar is exactly that out-of-band channel.

Import works without a sidecar too (generating keys with the mapping tables plus `<group-path>.<entry-id>`), but the **original Key would change**, which breaks the lossless round trip and the correspondence with existing archives. Therefore:

> [!IMPORTANT]
> **Please move, commit and distribute the `.clif` file and the same-named `.clifmap.json` together.**

## Structure

```json
{
  "version": 1,
  "namespace": "p-clifl10n-suite",
  "entries": [
    {
      "id": "p-clifl10n-suite.clif-localization-suite-property-names.clif-localization-suite-settings.entry-f78120e8",
      "namespace": "UObjectDisplayNames",
      "key": "ClifLocalizationSuiteSettings:bAutoRepairClif",
      "clan": "clif-localization-suite-property-names",
      "culture": "zh-Hans"
    }
  ]
}
```

| Field | Type | Description |
|:---|:---|:---|
| `version` | `int` | Sidecar structure version, currently `1` |
| `namespace` | `string` | The CLIF header's `namespace` (the CLIF Namespace setting in effect at export time) |
| `entries` | `array` | The entry mapping table |
| `entries[].id` | `string` | The CLIF canonical ID: `<namespace>.<clan>.<group-path>.<entry-id>` |
| `entries[].namespace` | `string` | The original **UE Namespace** |
| `entries[].key` | `string` | The original **UE Key** |
| `entries[].clan` | `string` | The entry-level clan (semantic family) |
| `entries[].culture` | `string` | The target language this entry belongs to |

Encoding: UTF-8 without BOM, pretty-printed (`PrettyJsonPrintPolicy`).

## Discovery order

Import (GUI, CLI and the AI pipeline) looks for the sidecar automatically:

1. The `<file name>.clifmap.json` **in the same directory** as the imported `.clif`
   (example: `zh-Hans/clif-game.clif` → `zh-Hans/clif-game.clifmap.json`)
2. The `<manifest stem>.clifmap.json` in the parent directory
   (example: `zh-Hans/clif-game.clif` → `Game.clifmap.json`)
3. Neither found → generate the Key with the `Clan to Namespace` mapping plus `<group-path>.<entry-id>`, and record a warning:
   `Sidecar '<path>' could not be loaded; falling back to algorithmic Namespace/Key mapping.`

> [!TIP]
> Sidecar lookup is based on the file **path** rather than a content hash, so moving the whole export directory somewhere else does not affect restoration.

## Restore rules

When importing each entry:

```text
canonical = document.GetCanonicalId(group, entry)     # namespace.clan.group.entry
if (sidecar 命中 canonical) {
    UE Namespace = sidecar.namespace
    UE Key       = sidecar.key
} else {
    UE Namespace = 语义映射(clan) 或 CLIF namespace
    UE Key       = "<group-path>.<entry-id>"
}
```

Key points:

- The `id` in the sidecar only takes effect if it matches the current document's canonical ID **exactly** (case sensitive)
- A sidecar file may accumulate entries from multiple cultures and multiple exports: records with different `culture` values in the same file do not interfere with each other
- A corrupt sidecar or a JSON parse failure **does not abort the import**; it only adds a warning and falls back to the algorithmic mapping

## When it is written

| Condition | Behaviour |
|:---|:---|
| `bWriteSidecar = true` (the default) and `OutputDirectory` is not empty | Writes `<OutputDirectory>/<manifest stem>.clifmap.json` |
| `OutputDirectory` is empty (build the document structure only, write nothing to disk) | No sidecar is written |
| Export through the AI pipeline | The sidecar is written to `Saved/ClifAITranslate/<Target>/` and copied back to the Target data directory along with the translation artefacts |
